## Consulting execution

Consulting execution is optional and follows an accepted proposal whose engagement model is consulting, assessment, training, managed service, or the non-software scope of a mixed engagement, or an explicit engagement agreement the user supplies. `q-consult-workflow` is its root orchestrator and single global state writer; it accepts the exact accepted proposal version and never edits it. For an external agreement, it registers the exact user-confirmed version as an immutable `engagement-agreement`; in either path, the engagement plan's commitment register is the single source of `DEL-nnn` and `AC-nnn` IDs by literal reference to the commercial source.

Its stages are canonical only for the engagement plan and commitment register, the assessed current state and its evidence, the intervention design and each deliverable's declared scope, and the recorded client acceptance. Consulting records use three distinct classes: an `engagement-record` is authored, supporting evidence with `authority_scope: engagement-evidence` and an explicit `classification`; a `working-document` is authored and supporting while `Working`, then becomes `Archived` when its deliverable is released; a `consulting-deliverable` is authored and canonical only for the declared scope and carries a `deliverable_kind` selected from `q-core-identity/references/document-kinds/`.

A simple deliverable is one canonical Markdown file. A compound deliverable uses `03-deliverables/<DEL-id>/deliverable.md` as its sole canonical meaning; registered components are `derived` with `semantic_authority: none` or authored `supporting`, and each has `source_refs: ["<ART-id>@<version>"]` resolving to the canonical deliverable. A component is never canonical. A manual or runbook for delivered software is a `consulting-deliverable` only when the commercial commitment lists it as a service deliverable; otherwise it is a delivery release note or delivery evidence. A client-owned document is never copied into the artifact index: register it as `EVD-nnn` with locator and classification, and register only an authorized extraction as derived.

Confidentiality is monotonic. `restricted` source content is never persisted: retain only its locator and an authorized redacted summary. `confidential` content stays inside the engagement artifact root and is excluded from any render or report with a lower classification. A derived artifact channel or report inherits the maximum classification of every source; no renderer may lower it.

An outline before a consulting deliverable is optional and triggered only by size or an explicit request for structural approval. Making it universal is ceremony unrelated to risk; the default path authors the deliverable directly.

A diagnostic finding cites registered evidence or remains a hypothesis; the remedy is designed only from confirmed findings. Before the design gate, documentation QA runs through `q-consult-intervention`; the root orchestrator then marks the confirmed intervention design and exact deliverable versions `Baselined`. Acceptance presents only those `Baselined` versions and records the client's disposition per deliverable and version, never inferred from internal review, a delivered file, or silence. The `execution-release` names exact accepted versions, marks only those versions `Released`, is immutable, and is the "approved execution results" reporting consumes. A deviation from accepted scope, price, schedule, deliverables, acceptance criteria, or other commitments returns to proposal change control; a client-facing render of a deliverable is produced through the reporting channel, stays derived, and is not a component; a diagnostic or intervention candidate from ideation enters only through the owning stage's own procedure.
